# 1 Introduction（引言）

## 1.1 研究背景与问题陈述

高精度文档解析已成为大语言模型（LLM）训练数据构建、检索增强生成（RAG）与智能文档处理（Intelligent Document Processing, IDP）的基础设施环节。与传统光学字符识别（OCR）仅追求字符转写不同，当代「解析」任务要求系统在复杂版式、多模态元素与真实成像退化条件下，恢复**阅读顺序、表格逻辑结构、数学公式、图表语义**以及可直接下游消费的 **Markdown / JSON / HTML** 等结构化表示。近年来，视觉语言模型（Vision-Language Model, VLM）与专用版面分析模型的结合，推动文档解析从「检测—识别级联 Pipeline」向「版面—内容解耦协同」与「端到端文档理解」两条路线并行演进。要在工程与学术层面构建可对比、可复现的高精度解析方案，必须厘清当前最具代表性的开源系统及其模块级能力边界——尤其是 **PaddleOCR-VL-1.5**、**MinerU2.5-Pro-2604-1.2B** 以及 Paddle 生态中面向表格的 **通用表格识别 v2 产线（PP-TableMagic）** 各子模块的分工与互补关系。本文后续章节将在上述技术基线之上，展开我们所提出的高精度解析方案；本节则对三者进行系统性介绍，为全文奠定概念与术语基础。

## 1.2 PaddleOCR-VL-1.5：轻量 VLM 与真实场景文档解析

### 1.2.1 定位与发布背景

**PaddleOCR-VL-1.5** 是百度飞桨团队于 2026 年 1 月发布的文档解析旗舰模型，参数量约 **0.9B**，在公开基准 **OmniDocBench v1.5** 上报告 **94.5%** 的整体精度，并面向 **扫描、倾斜、弯折、屏幕拍摄、复杂光照** 等五类真实退化场景（Real-World Challenges）进行专项优化。与仅强调字符错误率（CER）的传统 OCR 不同，PaddleOCR-VL-1.5 明确采用 **「版面分析 + 元素级 VLM 识别 + 结构化后处理」** 的完整产线范式：单独调用 VLM 权重或通过 OpenAI 兼容接口直推整页图像，均不能等价于官方完整流程，否则易出现版面错位引发的语义幻觉与结构丢失。

### 1.2.2 两阶段协同架构

PaddleOCR-VL-1.5 的核心流水线可概括为：

```
整页文档图像/PDF
    → 阶段一：PP-DocLayoutV3（版面分析）
    → 裁剪各语义区域子图 + 阅读顺序
    → 阶段二：PaddleOCR-VL-1.5-0.9B（元素级识别）
    → 后处理（跨页表格合并、标题层级等）
    → Markdown / JSON 输出
```

**阶段一：PP-DocLayoutV3（统一版面分析引擎）**

PP-DocLayoutV3 是 PaddleOCR-VL-1.5 相对前代（含 PP-DocLayoutV2、以及 MinerU2.5 等同类版面方案）的关键升级，其设计目标直指 **非平面文档**（non-planar documents）：

| 能力维度 | 技术要点 | 意义 |
|----------|----------|------|
| 几何表示 | 由传统水平矩形框扩展为 **多点框 / 四边形 / 多边形**（rect / quad / poly / auto） | 适配倾斜、透视、弯折、拍照畸变 |
| 统一建模 | 在 **单一 Transformer 端到端架构** 内联合 **检测、实例分割、阅读顺序预测** | 减少「检测→排序」级联误差 |
| 推理效率 | 相对自回归大 VLM 做版式，显著降低延迟 | 适合产线化与高页数 PDF |

换言之，PP-DocLayoutV3 在一次前向传播中同时输出：区域类别、边界坐标、像素级分割与 **逻辑阅读顺序**，为后续 VLM 提供几何正确、顺序正确的输入，从源头抑制错误传播。

**阶段二：PaddleOCR-VL-1.5-0.9B（紧凑视觉语言模型）**

元素识别模型继承 PaddleOCR-VL-0.9B 的轻量架构，典型组成包括：

- **NaViT 风格动态分辨率视觉编码器**：对不同尺度、不同长宽比的子图自适应编码，兼顾精度与算力；
- **ERNIE-4.5-0.3B 语言解码器**：承担文本、表格、公式等序列化输出；
- **多任务扩展（1.5 相对 1.0）**：在文档解析（Document Parsing）之外，联合 **文本定位（Text Spotting / Grounded OCR）**、**印章识别** 等能力。

官方强调：VLM 对每个 **裁剪子图** 独立推理，再由后处理按 PP-DocLayoutV3 给出的顺序合并——因此 **版面阶段的框与顺序质量** 对最终 Markdown 结构具有 **级联放大效应**。

### 1.2.3 功能能力清单（产线级）

除基础正文 OCR 外，PaddleOCR-VL-1.5 产线通过 CLI / Python API / Docker Compose 服务化，支持以下可配置能力（与高精度解析密切相关）：

| 能力模块 | 说明 |
|----------|------|
| 异形框定位 | 全球首个在文档解析产线中系统支持 **多边形/四边形** 区域定位的公开方案之一，针对「歪文档」稳定输出 |
| 表格 / 公式 / 图表 | 对表格、公式、图表类区域调用 VLM 专用提示与分辨率策略；可选 `--use_chart_recognition` |
| 印章识别 | v1.5 新增 `--use_seal_recognition`，面向合同、票据等场景 |
| 文档预处理 | 可选文档方向分类（0°/90°/180°/270°）、文本图像矫正（UVDoc） |
| 多语言 | 支持 **109–111** 种语言（含藏语、孟加拉语等扩展） |
| 长文档 | **跨页表格合并**、**多级标题重建**（`restructure_pages`） |
| 输出格式 | 默认 Markdown + JSON；服务化场景可扩展 docx / html / latex |
| 推理加速 | VLM 环节可接 **vLLM / SGLang** 等专用服务，版面分析仍在 Paddle 侧本地执行 |

### 1.2.4 在文档解析技术谱系中的位置

PaddleOCR-VL-1.5 属于 **「解耦式 VLM 文档解析」** 路线：保留 Pipeline 的可控性与模块优化空间，同时用 0.9B 级 VLM 提升元素识别上限。与纯端到端大 VLM 相比，其优势在于 **部署成本、可解释性与真实场景鲁棒性（尤其异形框）**；与纯传统表格 Pipeline 相比，其在 **复杂版式、公式、图表** 上更依赖 VLM 语义建模。该路线也是本文高精度方案的重要对照基线之一。

## 1.3 MinerU2.5-Pro-2604-1.2B：数据引擎驱动的小参数 SOTA

### 1.3.1 定位与核心主张

**MinerU2.5-Pro-2604-1.2B**（下文简称 **MinerU2.5-Pro**）是上海人工智能实验室 OpenDataLab 团队 2026 年发布的文档解析 VLM 权重，挂载于开源工具链 **MinerU 3.x**。其 HuggingFace 模型 ID 为 `opendatalab/MinerU2.5-Pro-2604-1.2B`，参数量 **1.2B**，在 **OmniDocBench v1.6** 上取得 **95.69** 的综合得分——论文报告其 **在不改变 MinerU2.5 网络结构的前提下**，仅通过 **数据工程与三阶段训练策略** 便将同架构基线从 **92.98 提升至 95.69（+2.71）**，并声称超越包括 **PaddleOCR-VL-1.5、GLM-OCR** 及 **Gemini 3 Pro、Qwen3-VL-235B** 等专用或通用 VLM。

这一结果对高精度解析研究具有方法论意义：当多种架构在「相同困难样本」上呈现 **高度一致的错误模式** 时，性能瓶颈可能主要来自 **训练数据覆盖度、难例标注质量** 而非结构创新本身；MinerU2.5-Pro 正是该「Data-Centric」路径的集中体现。

### 1.3.2 模型架构（继承 MinerU2.5，未改结构）

MinerU2.5-Pro 完全继承 **MinerU2.5** 的 **1.2B 解耦式粗到细（coarse-to-fine）架构**：

| 组件 | 规格 | 作用 |
|------|------|------|
| 视觉编码器 | **NaViT-675M** | 原生分辨率文档图像编码，控制 token 规模 |
| 语言模型 | **Qwen2-0.5B** | 结构化文本 / Markdown 生成 |
| 范式 | **Decoupled VLM** | 在统一模型内协调 **版面分析** 与 **内容识别**，兼顾 Pipeline 可控性与 VLM 语义能力 |

与 PaddleOCR-VL-1.5「独立 PP-DocLayoutV3 + 独立 0.9B VLM」的 **显式两模型产线** 不同，MinerU2.5 系列更强调 **单一 1.2B 模型内部的阶段化解耦**；但对外部署时，MinerU 工具链仍提供 **pipeline 后端** 与 **vlm 后端（vLLM 加速）** 两种工程路径。

### 1.3.3 Data Engine：精度提升的来源

MinerU2.5-Pro 的技术报告将增益归因于三大数据引擎组件与配套训练：

**（1）DDAS（Diversity-and-Difficulty-Aware Sampling）**

- 训练规模由不足 **10M** 页扩展至 **65.5M** 页；
- 在扩大覆盖的同时控制分布偏移，强化 **长尾场景**（复杂嵌套表、密集公式等）采样。

**（2）CMCV（Cross-Model Consistency Verification）**

- 利用 **异构模型输出一致性** 评估样本难度；
- 为难例生成更可靠的伪标注，缓解「难例自动标注不可信」 paradox。

**（3）Judge-and-Refine 标注流水线**

- 对 hard samples 采用 **渲染—验证—迭代修正** 策略，提升表格结构、LaTeX 公式等 **高错误率标注** 的质量。

**三阶段训练策略**：大规模预训练 → 高质量难例微调 → **GRPO 格式对齐**，与数据质量分层相匹配。

### 1.3.4 解析能力与工程特性

相对 MinerU 2.5 基线，MinerU2.5-Pro 在能力上强调：

| 维度 | 能力 |
|------|------|
| 评测指标 | 文本 Edit Distance **0.036**；Dense Formula（CDM）**97.29**；表格 TEDS 在 OmniDocBench 等基准上相对基线 **+5.54** 量级提升（见模型 README） |
| 表格 | 在 5 个表格基准上报告领先，强调 **复杂/嵌套表** |
| 新增实用特性 | **图像与图表解析**、**截断段落合并**、**跨页表格合并**、**表格内图像识别** |
| 多格式原生解析 | MinerU 3.1+ 支持 **PDF、DOCX、PPTX、XLSX** 及图像，面向端到端办公文档流 |
| 部署 | CLI、`vlm-http-client` + OpenAI 兼容服务、Web API、Gradio、Router；VLM 后端基于 **vLLM**（Volta+ GPU，显存 ≥8GB，CUDA 12.9.1+） |

### 1.3.5 与 PaddleOCR-VL-1.5 的对比视角（引言小结）

| 对比项 | PaddleOCR-VL-1.5 | MinerU2.5-Pro-2604-1.2B |
|--------|------------------|-------------------------|
| 参数量 | ~0.9B（VLM 部分）+ 独立版面模型 | 1.2B 统一架构 |
| 版面 | **PP-DocLayoutV3** 独立模块，异形框/阅读顺序联合 | 模型内解耦式版面—内容 |
| 精度报告 | OmniDocBench **v1.5：94.5%** | OmniDocBench **v1.6：95.69** |
| 主要创新叙事 | 真实场景异形框 + 多任务 0.9B VLM | **数据引擎** + 评测协议 v1.6 |
| 工具形态 | PaddleOCR 产线 / Docker / paddlex serve | MinerU 工具链 + 云端 API |
| 表格深度 | 依赖 VLM 元素识别 + 可选 PP-Structure 模块 | 数据驱动强化 + 跨页表合并等后处理 |

二者代表当前开源高精度解析的 **双旗舰**：前者以 **模块化版面 + 超轻 VLM** 强调落地与真实畸变；后者以 **小模型 + 大规模数据工程** 刷新基准上限。本文的高精度方案将在后续章节与二者进行能力对齐与实验对照。

## 1.4 Paddle 表格产线：PP-TableMagic 与各模块能力

表格是高精度文档解析中 **误差最敏感、结构恢复最难** 的要素之一。纯 VLM 端到端输出 Markdown 表格虽便捷，但在 **有线表、无线表、合并单元格、嵌套表** 等场景下，专用表格 Pipeline 仍常作为 **精度兜底、可微调、可解释** 的互补路径。PaddleOCR 提供 **通用表格识别 v2 产线（PP-TableMagic）**，并在 **PP-StructureV3** 文档分析产线中作为可选 **表格识别子产线** 集成。该产线采用 **「表格分类 → 结构识别 / 单元格检测 → 文本检测识别 → HTML 组装」** 的多模型串联策略，相对早期仅依赖 SLANet 类结构模型的方案，显著提升了 **有线/无线分治** 与 **端到端 TEDS** 表现。

### 1.4.1 产线总体流程

```
输入表格区域图像（或整页中的 table 区块）
    → [可选] 文档方向分类 / 文本图像矫正 / 版面区域检测
    → 表格分类（有线 / 无线）
    → 分支 A：表格结构识别（SLANet / SLANet_plus / SLANeXt_*）
    → 分支 B：表格单元格检测（RT-DETR-L_*）
    → 单元格内文本：文本检测（PP-OCRv5_det）+ 文本识别（PP-OCRv5_rec）
    → 逻辑组装 → HTML（及可转 Markdown 的表格结构）
```

产线设计哲学是：**先判别表格类型，再选择专用结构与检测权重**，避免「一种结构模型打天下」在无线表或复杂表上的失效。

### 1.4.2 核心模块能力说明

#### （1）表格分类模块（Table Classification）

| 项目 | 内容 |
|------|------|
| 默认模型 | **PP-LCNet_x1_0_table_cls** |
| 能力 | 判别 **有线表（wired）** 与 **无线表（wireless）**（Top-1 Acc 约 **94.2%**） |
| 作用 | 为后续 **结构识别模型** 与 **单元格检测模型** 的路由提供依据 |
| 独立部署 | `paddleocr table_classification` / `TableClassification` API |

该模块计算量极小（毫秒级），却是整个表格 Pipeline **降低误路由** 的第一道关口。

#### （2）表格结构识别模块（Table Structure Recognition）

| 模型系列 | 特点 | 适用 |
|----------|------|------|
| **SLANet** | PP-LCNet + CSP-PAN + SLA Head，轻量 CPU 友好 | 基础有线表结构 |
| **SLANet_plus** | 加强无线表与复杂表，降低对定位偏移敏感度 | 通用升级款 |
| **SLANeXt_wired / SLANeXt_wireless** | 新一代结构模型，**有线/无线分训权重**，有线表能力提升显著 | PP-StructureV3 默认高端配置 |

能力：预测 **表格行列逻辑结构** 与 **单元格坐标关系**，输出可转为 HTML 骨架。  
独立 CLI：`paddleocr table_structure_recognition`。

#### （3）表格单元格检测模块（Table Cells Detection）

| 项目 | 内容 |
|------|------|
| 有线表模型 | **RT-DETR-L_wired_table_cell_det**（mAP 约 **82.7%**） |
| 无线表模型 | **RT-DETR-L_wireless_table_cell_det** |
| 原理 | 基于 **RT-DETR-L** 实时检测器，在自建单元格数据上预训练 |
| 能力 | 像素级/框级 **单元格定位**，支撑合并单元格、不规则网格 |
| 扩展模式 | `use_wired_table_cells_trans_to_html`：可由 **单元格几何关系直接构建 HTML**，绕过部分结构模型路径 |

独立 CLI：`paddleocr table_cells_detection`。

#### （4）文本检测与识别模块（支撑单元格 OCR）

表格产线内单元格文字通常走 **PP-OCRv5** 系列：

| 模块 | 推荐模型 | 能力 |
|------|----------|------|
| 文本检测 | **PP-OCRv5_server_det** / mobile_det | 单元格内多行、密集文本定位 |
| 文本识别 | **PP-OCRv5_server_rec** | 简中/繁中/英/日等多语种、手写/竖排等 |

表格 **结构正确但 OCR 错误** 仍会导致 TEDS 下降，因此表格产线必须与 **高精度 OCR 子系统** 协同调优。

#### （5）可选前置与上下文模块

在 PP-StructureV3 或独立表格场景中，还可串联：

| 模块 | 模型示例 | 作用 |
|------|----------|------|
| 文档图像方向分类 | PP-LCNet_x1_0_doc_ori | 整页/整表旋转校正 |
| 文本图像矫正 | UVDoc | 透视/弯曲矫正 |
| 版面区域检测 | PP-DocLayout_plus-L 等 | 先定位 table 区域再送入表格产线 |

### 1.4.3 与 PP-StructureV3 的关系

**PP-StructureV3** 是 Paddle 面向 **整页文档 → Markdown** 的通用结构化产线，在 PP-StructureV1 基础上强化：

- 版面区域检测、表格、公式、印章、图表理解；
- 多栏 **阅读顺序恢复**；
- 可选 **表格识别子产线**（即上述 PP-TableMagic 能力）。

典型调用：

```python
from paddleocr import PPStructureV3
pipeline = PPStructureV3(use_table_recognition=True)
```

通过 `wired_table_*` / `wireless_table_*` 等参数，可对 **有线/无线表** 分别指定结构识别与单元格检测模型，实现 **表格路径可配置、可微调、可服务化**——这与 VLM 产线中「表格作为 VLM 一种 prompt 类型识别」形成 **互补双轨**：工程上常见策略是 **VLM 负责版式与语义，表格 Pipeline 负责 TEDS 敏感场景** 或 **VLM 失败回退**。

### 1.4.4 对高精度解析研究的启示

PP-TableMagic 体现了高精度表格解析的三条原则，与本文主题直接相关：

1. **分类型建模**（wired/wireless）优于单一结构头；
2. **结构 + 检测 + OCR 三级串联** 仍是在可解释性与 TEDS 指标上的强基线；
3. **模块独立训练与部署** 便于针对金融报表、科研表格等领域 **微调单一环节** 而不重训整页 VLM。

因此，在讨论 PaddleOCR-VL-1.5 或 MinerU2.5-Pro 的「端到端高精度」时，不应忽略 Paddle 表格产线作为 **表格专项精度锚点** 的价值。

## 1.5 当前高精度 OCR / 文档解析面临的主要问题

尽管 PaddleOCR-VL-1.5、MinerU2.5-Pro 等系统不断刷新公开基准，但在 **面向生产的「高精度解析」** 语境下，学界与工业界仍面临一系列尚未充分解决的问题。将这些问题置于 Introduction 中加以明确，有助于说明：**高精度不仅指基准分数接近 100%，更指在真实数据、真实约束下结构可信、结果可用、系统可运维**。结合 §1.2–§1.4 所介绍的代表性方案，可将当前瓶颈归纳为以下七个方面。

### 1.5.1 任务定义与评测口径不统一

「高精度 OCR」在文献与产品中存在 **语义漂移**：

| 表述 | 实际含义 | 风险 |
|------|----------|------|
| 低 CER / 低 Edit Distance | 字符或文本行转写正确 | 无法反映表格结构、阅读顺序、标题层级 |
| 页级解析分数（如 OmniDocBench） | 版面 + 多元素综合 | 不同系统匹配规则、输出粒度不一致时可产生 **评分虚高或不可比** |
| 端到端 Markdown 可读性 | 人眼或 LLM 下游可用 | 与 TEDS、CDM 等 **结构指标** 可能脱节 |

MinerU2.5-Pro 技术报告已指出：OmniDocBench v1.5 存在 **元素匹配偏差** 与 **难例占比不足**，并据此提出 v1.6 的 Hard 子集。换言之，**高精度研究首先面临「评什么、怎么评」的问题**；在评测协议未对齐前，跨系统对比与方案选型均存在争议。

### 1.5.2 完整产线与「仅 VLM」混用导致的精度假象

如 §1.2 所述，PaddleOCR-VL 官方明确：**仅调用 VLM 组件或通过 OpenAI 兼容接口对整页图像推理，不等于完整 PaddleOCR-VL 流程**。实践中常见误用包括：

- 将 VLM 服务当作通用「看图说话」接口，忽略 **版面检测与阅读顺序**；
- 在 RAG 流水线中直接消费 VLM 输出的 Markdown，未校验 **表格 HTML / 公式 LaTeX** 的结构合法性。

其后果是：公开基准上 SOTA 模型的能力无法复现，且产生 **幻觉段落、错序阅读、表格错位** 等在生产中代价极高的错误。高精度解析的首要工程原则应是 **流程完整性可验证**，而非单次模型推理分数。

### 1.5.3 级联误差与多模块协同难题

无论是 **显式多模型产线**（PP-DocLayoutV3 → VLM → 后处理），还是 **表格 Pipeline**（分类 → 结构/检测 → OCR → HTML），亦或是 **解耦式 1.2B VLM** 内部的阶段化推理，本质上均为 **多阶段系统**：

```
前一阶段错误 → 输入分布偏移 → 后一阶段放大 → 最终 Markdown 结构崩溃
```

典型级联失效包括：

- **版面框偏移** 导致 VLM 在错误裁剪图上「正确认字但放错位置」；
- **表格分类路由错误**（有线/无线）导致结构模型与单元格检测模型不匹配；
- **跨页表格、多栏排版** 在单页最优策略下 **全局不一致**。

PaddleOCR-VL-1.5 通过 PP-DocLayoutV3 统一版面与顺序、MinerU2.5-Pro 通过数据引擎缓解难例，但 **均未从理论上消除级联结构**；高精度方案仍需在 **模块接口、置信度传递、失败回退** 上继续探索。

### 1.5.4 数据覆盖与难例标注的「天花板效应」

MinerU2.5-Pro 的实证表明：多种架构、多种参数规模的 SOTA 模型在 **同一批困难样本** 上失败模式高度相似，指向 **训练数据共性缺陷** 而非单一模型结构。该问题表现为两重矛盾：

1. **覆盖不足**：长尾场景（嵌套表、密集公式、低质扫描、特殊符号、古籍等）在训练分布中占比低，基准分数却可能已「饱和」；
2. **标注悖论**：最能提升模型的难例，往往 **最难被自动标注正确**（复杂表结构、LaTeX 公式、图表语义），噪声标注经监督微调直接固化为模型行为。

因此，**仅靠扩大参数或更换 backbone 难以突破天花板**；数据工程（采样、一致性校验、Judge-and-Refine）成为与架构创新并列的主攻方向，但也带来 **成本、版权与复现性** 新问题。

### 1.5.5 表格、公式、图表等结构化元素的「最后一公里」

§1.4 表明，表格仍是 **专用 Pipeline 与 VLM 双线作战** 的领域：

| 元素 | 主要难点 | 现状局限 |
|------|----------|----------|
| 有线/无线表 | 类型判别、合并单元格、嵌套 | VLM 输出 Markdown 表常缺语义；Pipeline 对版式偏移敏感 |
| 公式 | 行内/独立公式、印刷 vs 手写 | vLM 参数对行内公式影响有限；手写仍弱 |
| 图表 | 数据提取 vs 图像描述 | 需额外开启 chart 模块或 `image_analysis`；指标不统一 |
| 印章/手写批注 | 领域特定 | 需单独开关或领域数据 |

即便 OmniDocBench 总分超过 95%，**单元素指标**（如 TEDS、CDM）仍可能距离业务「零人工校对」有差距。高精度解析在 **元素级** 上仍是开放问题。

### 1.5.6 部署资源、时延与工程碎片化

高精度往往意味着 **GPU + 大模型 + 多服务**：

- VLM 推理（vLLM）对 **显存预分配** 敏感，同机多服务易 OOM；
- 版面分析、表格 Pipeline、VLM 可能分布在 **不同容器/进程**，增加网络与版本对齐成本；
- Apple Silicon、边缘设备 **无法复现 Docker + CUDA 路径** 下的加速能力；
- 云端 API（精准解析 Token、按页计费）与本地部署在 **成本、隐私、配额** 上权衡困难。

结果是：实验室 SOTA 与生产「高精度」之间存在 **工程鸿沟**——同一方案在 A100 集群与单机 RTX 消费卡上的 **精度—吞吐—成本** 曲线截然不同。

### 1.5.7 下游任务对齐与可信性（面向 LLM / RAG）

高精度解析的终极用户常是 **RAG、知识库、Agent**，其需求已超出 OCR 范畴：

- 需要 **块级元数据**（标题层级、表注、图注、页码）以支持引用与切片；
- 需要 **低幻觉、可校验** 的输出（公式可渲染、表格可重算）；
- 长文档需 **跨页逻辑**（表合并、章节连续），与单页最优解析冲突。

当前系统多输出「整页 Markdown」，对 **引用溯源、增量更新、人工审核接口** 支持不足。高精度若不能转化为 **下游可验证性**，在 LLM 应用中的价值将大打折扣。

### 1.5.8 与本研究的关系（问题—方案衔接段）

上述问题说明：**高精度文档解析仍是开放课题**，而非某一单点模型即可闭合。§1.2–§1.4 所介绍的 PaddleOCR-VL-1.5、MinerU2.5-Pro 与 Paddle 表格产线，分别代表了 **异形框版面 + 轻量 VLM**、**数据引擎 + 小参数 SOTA**、**表格模块化 Pipeline** 三条成熟路径，但均未单独解决 §1.5 中的全部瓶颈——尤其体现在 **复杂表格结构恢复** 与 **字体极度模糊、低质扫描类文档** 两类难例上。

针对上述痛点，本文并非从零训练单一超大模型，而是在 **复用与编排现有开源能力** 的前提下，形成可落地、可切换的两套解析路径；其设计要点在 §1.7 简要预告，技术细节与实验验证见后续章节。

## 1.7 本文工作概要（Introduction 末端贡献预告）

在充分吸收 §1.2–§1.4 代表系统能力边界、并正视 §1.5 所列开放问题的基础上，**本文已构建并验证一套面向生产的高精度文档解析方案**。遵循 Introduction「动机—现状—问题—贡献」的收束惯例，此处仅作 **高度概括**，不展开实现细节与超参数，以免与后续方法章重复。

### 1.7.1 面向复杂表格与极度模糊文档的开源能力编排方案

针对 **复杂表格结构**（有线/无线混合、合并单元格、嵌套表、跨页表等）与 **字体极度模糊、低对比度、扫描退化** 等难例文档，本文提出 **基于现有开源模型能力的组合式解析方案**：

- **不重复造轮子**：在版面分析、文档级 VLM、表格专项 Pipeline、通用 OCR 等层面，**调用并协同** PaddleOCR-VL / PP-StructureV3、PP-TableMagic（表格分类—结构—单元格—OCR）、MinerU 等已公开模型与产线，按文档类型与置信度进行 **路由与回退**；
- **难点定向增强**：对表格敏感场景优先走 **表格模块化产线** 以锚定 HTML/TEDS；对版式复杂或畸变严重的页面，结合 **异形框版面检测 + 多任务 VLM** 保证阅读顺序与块级结构；对模糊文本区域，在产线内串联 **检测—识别—后处理** 并辅以图像增强前置，降低级联误差；
- **流程可验证**：强调 **完整产线调用** 而非单点 VLM 推理，使「高精度」对应可复现的结构化输出（Markdown / HTML 表 / 元数据），而非仅字符转写分数。

该路径面向 **精度优先、GPU 资源可保障** 的部署场景（如本地 Docker + vLLM 服务、多容器协同），与 §1.2、§1.4 所代表的开源生态 **直接对齐**。

### 1.7.2 轻量化产线方案

在同等问题设定下，本文同时给出 **轻量化产线（Lightweight Pipeline）** 方案，用于 **算力受限、时延敏感或边缘侧** 等场景：

- 以 **Mobile / Server 轻量检测识别模型、精简版面模块** 为主干，减少 VLM 调用频次或采用更小参数推理路径；
- 保留 **「表格难例 → 专项子产线、其余版面 → 轻量 OCR / 精简结构」** 的分级策略，在 **精度—吞吐—显存** 之间可配置权衡；
- 与 §1.7.1 方案 **共享同一套编排逻辑与接口约定**，便于在同一业务系统中按 SLA 切换「高精度模式」与「轻量模式」。

### 1.7.3 贡献陈述（供摘要与审稿对照）

综合而言，本文主要贡献可概括为：

1. **问题梳理**：系统归纳高精度文档解析在评测、级联误差、数据天花板、结构化元素与部署等方面的关键挑战（§1.5）；
2. **开源编排方案**：针对 **复杂表格** 与 **极度模糊文档** 两类硬样本，给出 **调用并组合现有开源模型能力** 的可复现高精度解析流程（§1.7.1，详见后续方法章）；
3. **轻量化产线**：提供与高精度路径 **同构、可切换** 的轻量产线设计，满足资源受限场景（§1.7.2，详见后续方法章）；
4. **实验与对比**（后续章节）：在 [待填：数据集/业务样本] 上与 §1.2–§1.4 基线及消融设置进行对比，验证上述两类方案的有效性。

## 1.8 本节小结与全文结构预告

综上所述，当前高精度文档解析领域已形成清晰的技术分层，同时仍受 **评测统一性、流程完整性、级联误差、数据天花板、结构化元素短板、部署碎片化与下游可信性** 等多重约束（§1.5）：

- **PaddleOCR-VL-1.5** 以 **PP-DocLayoutV3 异形框版面 + 0.9B 多任务 VLM** 为核心，面向 **真实场景畸变与长文档结构化**，强调 **完整产线不可拆分**；
- **MinerU2.5-Pro-2604-1.2B** 在 **1.2B 不变架构** 下通过 **65.5M 级 Data Engine** 将 **OmniDocBench v1.6** 推至 **95.69**，代表 **data-centric** 精度突破路径；
- **Paddle 表格产线（PP-TableMagic）** 以 **表格分类、结构识别、单元格检测、OCR** 四模块协同，提供 **HTML 级表格恢复** 与 **可微调 Pipeline**，是 VLM 表格能力的重要对照与补充。

三者共同定义了能力上限与模块边界；§1.5 明确了尚待解决的关键问题；**§1.7 则预告本文针对复杂表格与极度模糊文档所提出的开源能力编排方案，以及与之配套的轻量化产线**。全文结构安排如下（章节编号可按实际稿件调整）：

| 章节 | 内容 |
|------|------|
| 第 2 章（或并入第 1 章） | 问题分析、相关工作的补充与评测协议说明 |
| 第 3 章 | **高精度编排方案**：开源模型选型、路由策略、复杂表格与模糊文档处理流程 |
| 第 4 章 | **轻量化产线**：模块裁剪、推理路径与资源—精度权衡 |
| 第 5 章 | 系统实现与部署（Docker / API / 服务编排等） |
| 第 6 章 | 实验、对比与讨论 |
